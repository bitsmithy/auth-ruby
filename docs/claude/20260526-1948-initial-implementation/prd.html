Layers in scope
Problem · Solution

Why this gem exists.

The bitsmithy portfolio ships in Ruby, Python, and Go. Every phone-OTP implementation has been drifting from the others. This gem is the reference implementation that ends the drift.

Current state

Every app rebuilds the same plumbing — a verifications table, an OTP generator with expiry and attempt caps, gem-side rate limiting, a Twilio integration, a sessions controller, JWT or session encoding, Phone normalisation.

Each implementation drifts from the others. Each independently has to worry about SMS pumping fraud. Three flavours of the same code across three apps — across three languages — is unfun and lower quality than centralising it once.

After v0.1.0

One configure block; send_code, verify_code, decode_token; an optional Rails Controller concern. Twilio Verify owns OTP lifecycle, so no local verifications table exists.

Identity is a Verification artifact carrying a Phone — never a User. The Host app maps a verified Phone to its own user records however it wants. The gem stays narrow; lifecycle decisions stay with the apps that need to make them.

User Stories · 33 total

Six actors, one contract.

Stories are grouped by actor. Each actor represents a different vantage point on the same gem; together they define the surface area we must hold true.

Host-app dev

Integration

9 stories
  1. Configure the gem in one initializer block with Twilio credentials and a Signing key.
  2. Clear boot-time failure if any required config is missing.
  3. send_code accepts any plausible Phone format; normalisation is internal.
  4. Result-returning methods for expected failures (wrong code, rate-limited, Twilio outage).
  5. decode_token raises on tampered/expired Tokens — no nil-checks at every read site.
  6. Rails Controller concern exposes current_phone, authenticated?, sign_in, sign_out.
  7. Own the unauthenticated-redirect decision — no require_authentication! baked in.
  8. Use the gem from non-Rails code (CLI, Rake, Sidekiq) — core API needs no Rails.
  9. Same Identity contract across Ruby, Python, Go implementations.
Host-app dev

Error handling

4 stories
  1. Twilio failures categorised into four symbols — page oncall on auth errors, show "try again" for service outages.
  2. :invalid_phone_number Result for unparseable Phone input.
  3. :invalid_code Result when the user types the wrong OTP.
  4. :rate_limited Result when too many send_code calls hit the same Phone in the window.
End user

Verification flow

6 stories
  1. Enter Phone, receive SMS.
  2. Format-agnostic input — spaces, dashes, parens, dots, raw E.164 all accepted.
  3. "Please wait" feedback when rate-limited.
  4. Enter six-digit code, get signed in.
  5. Wrong-code attempt fails clearly and allows retry.
  6. Stay signed in for ~24 hours without re-verifying.
Operator

Running in production

8 stories
  1. Exception messages redact Phones (per ADR-0004) — Sentry/Honeybadger never index full numbers.
  2. Public redact_phone helper for use in Host-app log statements.
  3. Default Rate limit (5 sends per Phone per hour) before Twilio is called — abuse incidents capped.
  4. Pluggable Store interface — swap to Redis when single-process state stops being enough.
  5. Signing-key rotation is viable; consequence = all Tokens invalidated.
  6. Stateless Tokens (ADR-0001) — authenticated request handling never hits a runtime store.
  7. test_mode! refuses in production-like envs and outside Rails (ADR-0002).
  8. Gem itself never logs a Phone — logging contract belongs to the Host app.
Test author

Testing Host apps

3 stories
  1. Test mode swaps the OTP adapter — controller and feature tests run without Twilio.
  2. Magic OTP "000000" always verifies in Test mode.
  3. Test mode send_code always succeeds — no Twilio mocks needed.
Maintainer

The gem itself

3 stories
  1. OTP::Adapter interface small enough that a VonageAdapter or MessageBirdAdapter could ship later without breaking the public surface.
  2. Controller concern conditionally loaded only when ActionController is defined — non-Rails apps incur zero Rails-load cost.

Implementation Decisions

Result, or raise?

Methods that fail on expected user input return a Result. Methods that fail only on programmer error or tampering raise. The convention applies to all of Layer 1's public surface.

Method On success On failure Why
send_code(phone) Result.success Result.failure Rate limits and Twilio outages are expected — branchable.
verify_code(phone, code) Result.success(+token) Result.failure Wrong codes are normal user flow, not exceptional.
decode_token(token) Identity raises InvalidToken Bad Token means tampering or expiry — not normal flow.
normalize_phone(input, country:) String (E.164) raises InvalidPhoneNumber Caller validates at boundary; reaching here invalid = bug.
configure { |c| ... } Config raises ConfigurationError Missing config is boot-time, not a runtime branch.
test_mode! Config (mutated) raises ConfigurationError Misuse in production is a developer error (ADR-0002).
redact_phone(phone) String (masked) — Pure transformation; cannot fail.
Error Symbol Vocabulary

Nine symbols, three sources.

Every Result.failure a Host app sees carries one of these. Originate either gem-side, in Twilio's Verify API, or in our own normalisation logic.

Symbol Source Meaning Host-app response
:invalid_phone_number gem / Twilio 60200 Phone failed normalisation, or Twilio rejected the format. Inline form error.
:invalid_code Twilio Verify User typed the wrong OTP. Re-render verify step with inline error.
:rate_limited gem Gem-side Rate limiter triggered (default 5/hour/Phone). "Please wait" message.
:max_send_attempts Twilio 60203 Twilio's per-Phone send cap reached. "Please wait" message (back off longer).
:max_check_attempts Twilio 60202 Too many verification attempts against one code. Force a re-send.
:twilio_authentication_error Twilio 401 Host app's Twilio credentials are wrong. Page oncall — not a user-facing issue.
:twilio_rate_limited Twilio 429 Twilio is throttling the whole account. Backoff with jitter; alert oncall.
:twilio_service_unavailable Twilio 5xx / timeout Twilio is having an incident. Retry, or fail open with maintenance page.
:twilio_error fallback Unmapped Twilio error — investigate. Show "try again" toast; investigate log.
Token · Config

What's on the wire, what's in config.

The Token is a stateless HS256 JWT (ADR-0001). Config holds Twilio credentials, the Signing key, and the two tunable defaults that affect Host-app behaviour.

Token claims
sub Verified Phone in E.164. String
iat Time the Token was issued. Integer · Unix
exp iat + session_duration (24h default). Integer · Unix
iss Always "bitsmithy-auth" — verified on decode. String
Config fields
twilio_account_sid From Twilio console. required
twilio_auth_token From Twilio console. required
twilio_verify_service_sid Per-Host-app Verify Service. required
signing_key ≥ 32 bytes random; HMAC secret. required
session_duration Token lifetime in seconds. 86_400 (24h)
rate_limit { per_phone:, window: } 5 / 1h
otp_adapter Swappable — TwilioAdapter default. lazy default
rate_limit_store Pluggable — MemoryStore default. lazy default
PII Redaction

Phone numbers are masked in every exception the gem raises — +15555551234 becomes +1******1234 before reaching error trackers (per ADR-0004). The gem exports Bitsmithy::Auth.redact_phone as a public helper so Host apps can use the same redaction in their own log statements. Result#phone stays unredacted (the success path needs it); README will steer Host apps toward redact_phone(result.phone) in any log line.

Architectural Decisions

Six ADRs load-bearing for this PRD.

Each ADR captures a decision that's hard to reverse, surprising without context, and the result of a real trade-off. Stored at docs/adr/ at the repo root.

ADR-0001

Stateless JWT without revocation

Tokens are signed JWTs; sign_out only clears the session cookie. session_duration defaults to 24h. Hard revocation is the Host app's job if it ever needs it.

ADR-0002

Test mode is Rails-env-guarded

test_mode! raises unless Rails.env.test? or Rails.env.development? is true. No ENV escape hatch. Non-Rails contexts refuse outright.

ADR-0003

Verification primitive, not user system

The gem owns Verification only. User records, sign-up vs sign-in, phone-change flows, revocation lists — all Host-app concerns. No Bitsmithy::Auth::User will ever exist.

ADR-0004

Redact phones in exceptions

Phones in exception messages are masked to +1******1234. The gem ships redact_phone as a public helper for Host-app logs.

ADR-0005

Twilio Verify as OTP backend

Twilio Verify owns OTP generation, expiry, attempts, and SMS-pumping fraud detection. Gem never stores OTPs. ~$0.05 per verification is worth not maintaining the plumbing.

ADR-0006

Pattern A cross-language naming

Language goes in the repo name, NOT the package name. Gem: bitsmithy-auth. Repo: bitsmithy/auth-ruby. Module: Bitsmithy::Auth.

Out of Scope

What v0.1.0 deliberately does not do.

Each exclusion has a reason. "We ran out of time" is not one of them. Some are deferred; some are permanent boundaries the gem will never cross.

Concern Status Why excluded
Mountable Rails engine + default sign-in views v0.2.0 Right shared UI is unknown until 2–3 Host apps converge. Each writes its own ~30-line SessionsController in the meantime.
Install generator v0.2.0 Pairs with the engine. Premature until there's something worth generating.
Redis-backed Rate-limit Store v0.2.0 Interface is in place. Adapter ships when first Host app needs multi-worker correctness.
Voice / WhatsApp OTP channels later Twilio Verify supports both. Extending later is a one-symbol change.
Email OTP / TOTP / authenticator apps later Phone-only is the v0.1.0 scope. If we add these they'll likely be a different gem.
Per-Host-app SMS template overrides from the gem never (in-gem) Twilio Verify Services already support per-service templates Twilio-side.
Signing-key rotation with overlap window never (in-gem) Single key. Rotation = sign-out-all. Documented as a deliberate non-feature in ADR-0001.
Hard Token revocation never (in-gem) Host-app concern. Pattern documented in ADR-0001.
Phone-number-change primitives never (in-gem) Host-app concern. Implemented by re-running Verification against the new Phone.
Bitsmithy::Auth::User model, sessions table, gem-owned state never (in-gem) See ADR-0003. Cuts against the verification-primitive boundary.
require_authentication! Controller helper never (in-gem) Host apps own redirect semantics — the gem won't encode a single answer.
Automatic log scrubbing (Lograge filter, etc.) never (in-gem) The redact_phone helper is enough; Host apps wire logging themselves.
Testing Decisions

TDD by default. Behaviour over implementation.

Every public method has at least one happy-path and one failure-path test. Names read as sentences. One assertion per test where possible.

Framework Minitest (gem scaffold default).

Further Notes

Distribution, persistence, conventions.

Distribution

Consumed via gem 'bitsmithy-auth', github: 'bitsmithy/auth-ruby' Gemfile entries — not published to rubygems.org. The gemspec's allowed_push_host is intentionally commented out; flip it to GitHub Packages or a private registry later if needed.

Persistence

The gem has no opinion on persistence. A Host app integrating it does not need to add any migrations. The only persistent state is whatever the Host app chooses to do with the verified Phone (typically a users.phone column).

Signing key generation

README will tell Host apps to run SecureRandom.hex(32) and store the result in their secrets manager. The default session_duration (24h) is overridable per Host app — admin tools may want 1h, marketing sites may want 7d.

Cross-language portfolio

This gem is the reference implementation. bitsmithy/auth-python and bitsmithy/auth-go will mirror its public semantics: the verbs, the error symbols, the Identity shape, the Token claim structure. Decisions taken here are binding on those repos.
