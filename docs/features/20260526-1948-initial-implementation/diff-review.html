Before · After

What the gem could do, then and now.

Three axes that capture the delta: the scaffold module shape, the verification capability, and the test coverage. Before = at commit c6dffc3 (bundle gem output). After = at HEAD.

Before · scaffold

lib/bitsmithy/auth.rb contained exactly one module, one constant, and one placeholder exception class:

module Bitsmithy
  module Auth
    class Error < StandardError; end
    # Your code goes here...
  end
end

No public methods. No dependencies beyond jwt defaults from the scaffold. One test asserting the gem has a version number. Zero production behaviour.

After · v0.1.0

Eight public façade methods on Bitsmithy::Auth: configure, send_code, verify_code, decode_token, normalize_phone, redact_phone, test_mode!, reset_config!.

Thirteen source files across lib/bitsmithy/auth/, two layers, three runtime gem dependencies (jwt, phonelib, twilio-ruby), one optional Rails Controller concern conditionally loaded only when ActionController is defined.

Six ADRs document the load-bearing architectural choices. CONTEXT.md establishes twelve domain terms used consistently across docs, code, and tests.

Before · capability

To authenticate a phone, every host app in the bitsmithy portfolio reimplemented the same plumbing:

  • A verifications table for OTP storage
  • OTP generation, expiry, attempt counters
  • SMS-pumping fraud detection
  • Rate-limit logic, Twilio integration
  • JWT or session encoding
  • Phone normalisation

Three apps × three languages = nine flavours of the same ~200 lines, drifting from one another over time.

After · capability

One configure block, one send_code call, one verify_code call. Host apps:

  • Get a signed HS256 JWT (the Token) on successful verification
  • Receive an Identity back from decode_token carrying phone, issued_at, expires_at
  • Include Bitsmithy::Auth::Controller in ApplicationController for current_phone, authenticated?, sign_in(token:), sign_out
  • Map verified Phones to their own User model however they want

No verifications table — Twilio Verify owns OTP lifecycle. No User model in the gem — that's a Host-app concern.

Before · tests

One test in test/bitsmithy/test_auth.rb:

def test_that_it_has_a_version_number
  refute_nil ::Bitsmithy::Auth::VERSION
end

Useful as proof of scaffold correctness. Useless as behavioural coverage.

After · tests

44 tests · 59 assertions across nine files. Every public façade method has at least one happy-path and one failure-path test. The Twilio adapter has Mocha-stubbed coverage for all seven error-symbol mappings. The Rails Controller concern is tested through a minimal FakeController stub. The rate limiter is tested for boundary, isolation, window reset, and mutex-protected concurrent burst.

Test stack: Minitest, Mocha, rubocop-minitest, rubocop-rake. Shared setup via ConfigHelper mixin and RailsEnvStub module.

Verification flow

The dance a Host app drives.

Phone in, Token out, Identity on the way back. Twilio Verify owns the OTP lifecycle; the gem composes around it.

Code review

Good, bad, ugly, and a couple of questions.

Findings against the production code at HEAD, after the simplify pass. Two review agents (code-reviewer and refactor-cleaner) plus a three-axis simplify pass were applied — most issues they surfaced have been resolved.

Good

Solid choices worth keeping

  • Six ADRs cover the load-bearing decisions. Reading docs/adr/ in order tells the architectural story without needing the conversation transcript.
  • Result-vs-raise convention is rigorously applied. send_code / verify_code always return Result. decode_token / normalize_phone always raise. No accidental mix.
  • Lazy MemoryStore eviction. The delete_if sweep at the top of each increment bounds memory at active-key cardinality instead of lifetime-unique. Three lines, real fix.
  • Conditional Controller loading. Non-Rails Host apps incur zero Rails-related require cost. The defined?(ActionController) guard at lib/bitsmithy/auth.rb:13 is the right shape.
  • No magic numbers or strings. DEFAULT_SESSION_DURATION, DEFAULT_RATE_LIMIT, JWT_ISSUER, JWT_ALGORITHM, MAGIC_TEST_CODE — all named.
  • Per-file require chain. Each lib file declares its own dependencies via require_relative (siblings) or require (cross-directory). No incidental load-order coupling.
Bad

Concrete issues that should be fixed

  • TwilioAdapter#map_status_code covers 500..529, not 500..599. See lib/bitsmithy/auth/otp/twilio_adapter.rb:61. HTTP 530–599 falls through to :twilio_error instead of :twilio_service_unavailable. Flagged in fact-check; not yet fixed. Trivial single-line change. The PRD claim "5xx" is technically accurate; the implementation under-covers.
Ugly

Things that work but could bite later

  • Phone.parse returns the Phonelib::Phone object. Both Phone.normalized and Phone.redact consume it. If phonelib's API changes in a future major (it has done so before), every call site needs updating instead of just Phone.parse. Cost of fixing now: introduce a small value object. Cost deferred: cheap until phonelib breaks API.
  • MemoryStore O(n) sweep on every increment. Acceptable at personal-project scale, but a per-call full-hash scan will become a hot-path drag if call volume grows or unique-Phone cardinality climbs. Periodic sweep (every N calls, or every M seconds) is the obvious next step.
  • The rate-limiter swallows Config changes. @rate_limiter ||= in auth.rb:74 caches the limiter at first use. If a Host app calls configure a second time to tune rate_limit, the cached limiter ignores it until reset_config!. Latent gotcha; unlikely to bite in practice given config is usually set once at boot.
Questions

Worth confirming before v0.2.0

  • Test file organisation. test_auth.rb covers Phone, Token, Config, Result, MemoryStore, TestAdapter via the façade. Five concerns got dedicated files. Threshold for extraction was the Rubocop ClassLength limit, not module boundary. Is that the right heuristic, or should Phone / Config get their own files now?
  • Public Phone module surface. Phone.normalized, Phone.redact, and the private Phone.parse are not in the README's public API table. Bitsmithy::Auth.normalize_phone and Bitsmithy::Auth.redact_phone are. Is the convention "module-level helpers are private, façade methods are public"? Worth documenting if so.
  • Should sign_in take an Identity instead of a Token? Currently sign_in(token:) takes the JWT string. A Host app calling verify_code already has both the token and (via decode) the Identity. Taking the Identity directly would be more symmetric with current_identity. Trade-off: requires Host apps to do the decode call explicitly.
Decision log

Six ADRs, three inferred, all recoverable.

High-confidence decisions are sourced from ADRs in docs/adr/. Medium-confidence decisions are inferred from commit messages and code structure during the simplify pass.

High confidence

Stateless JWT without revocation

ADR-0001 · 24h default session_duration

Decision: Tokens are signed JWTs with no server-side revocation list. sign_out clears the session cookie but the Token remains cryptographically valid until exp.

Rationale: Stateless verification means authenticated requests never touch a runtime store. The grilling phase considered (B) a revocation list keyed by jti, and (C) opaque session IDs with server-side storage — both negate the architectural payoff of JWTs and force every Host app to provision a revocation store.

Escape hatch: Host apps that need hard revocation later can store a per-Phone not_before cutoff and reject Identities with issued_at before it. The gem stays stateless; revocation becomes a Host-app concern.

High confidence

Test mode is Rails-env-guarded

ADR-0002 · no environment-variable escape hatch

Decision: test_mode! raises ConfigurationError unless Rails.env.test? or Rails.env.development?. Non-Rails contexts refuse outright.

Rationale: The blast radius of accidentally enabling Test mode in production is total — every Phone can sign in by entering "000000". A soft warning would not be loud enough; hard guard with no ENV escape hatch keeps the failure mode local to development.

High confidence

Verification primitive, not user system

ADR-0003 · explicit no-s

Decision: The gem owns Verification only. No User record, no sessions table, no phone-change flow, no revocation list. Host apps build all of those.

Rationale: "What a verified Phone means" varies per Host app (Customer, Admin, Auto-created guest). Bundling user management would force one shape and pull stateful concerns into the gem, breaking multi-project reuse.

High confidence

Phone redaction is context-dependent

ADR-0004 · revised in slice 2

Decision: Successfully-parsed Phones surfacing in exceptions are redacted (+1******1234). Failed-parse inputs in InvalidPhoneNumber#message keep the raw form.

Rationale: A string that failed Phonelib parsing may not be a phone at all. Redacting destroys debuggability of "why did my input fail?" while providing marginal PII protection. The ADR was revised mid-slice once the practical trade-off became visible.

High confidence

Twilio Verify as the OTP backend

ADR-0005 · ~$0.05 per verification

Decision: Twilio Verify owns OTP generation, expiry, attempt limiting, and SMS-pumping fraud detection. The gem stores no OTPs locally.

Rationale: Bespoke OTP machinery is a meaningful surface to maintain (verifications table, code generation, expiry sweeper, attempt counter, fraud heuristics). Twilio Verify removes all of it for a flat per-verification cost.

Lock-in cost: Switching providers later means coordinated cutover across Host apps. The OTP::Adapter interface is provider-agnostic, so a future VonageAdapter could ship without breaking the public API.

High confidence

Pattern A — language in repo name, not package

ADR-0006 · binds three repos

Decision: Gem is bitsmithy-auth, repo is bitsmithy/auth-ruby, module is Bitsmithy::Auth. Siblings follow the same shape.

Rationale: Ruby's foo-bar → Foo::Bar convention. Naming the gem bitsmithy-auth-ruby would force Bitsmithy::Auth::Ruby (awkward) or fight the namespace convention via require_paths overrides.

Inferred · medium

Lazy MemoryStore eviction (not periodic sweep)

commit d38ec57 · simplify-pass fix

Decision: Expired entries are evicted by a delete_if sweep at the top of every increment call.

Inferred rationale: A code-review pass surfaced unbounded memory growth proportional to lifetime unique Phones. Lazy eviction is the simplest fix that bounds memory at active-key cardinality. A periodic sweep was considered (commit message documents this); the simpler lazy sweep was preferred for v0.1.0.

Confidence note: Reasoning is reconstructed from the commit message and the simplify-pass agent report. The choice is reversible — swapping to periodic sweep would be a contained change.

Inferred · medium

No Bitsmithy::Auth auto-require for TwilioAdapter

commit 1159d41 · refactor

Decision: lib/bitsmithy/auth.rb requires OTP::TestAdapter but not OTP::TwilioAdapter. Host apps using Twilio must add require "bitsmithy/auth/otp/twilio_adapter" in their initialiser.

Inferred rationale: Non-Twilio consumers (future Vonage / MessageBird adapters, or pure-Ruby tooling) should not pay the twilio-ruby load cost. Reciprocally, the Test adapter is always required because tests are universal.

Confidence note: Reasoning is reconstructed from the commit message ("each file requires what it directly uses") and from the dependency boundaries; the README documents the host-app contract.

Inferred · medium

sign_in takes only :token, not :phone

commit 109ed83 · slice 6

Decision: Bitsmithy::Auth::Controller#sign_in(token:) — no phone: parameter.

Inferred rationale: The Token's sub claim already carries the verified Phone, so a separate phone: argument would be duplication. PRD originally listed sign_in(phone:, token:); the implementation dropped phone: after Rubocop flagged it as unused. The PRD was fact-checked to match.

Confidence note: Reasoning recovered from the slice 6 commit conversation and the fact-check pass that updated the PRD. The deliberate divergence is documented in PRD's Controller card.

Re-entry context · a note from present-Hao to future-Hao
You're coming back to this gem in three months to add the Vonage adapter, or to ship the Mountable Rails engine, or just to debug a production incident. Here's what you should know that the code doesn't tell you.

Key invariants

  • The Token's sub claim is always the normalised E.164 Phone. Host apps that store the verified Phone do so off Identity#phone, NOT off the raw input.
  • test_mode! auto-fills signing_key only if it's unset. Production code paths that validated config first won't reach this branch.
  • The rate limiter holds the FIRST rate_limit values it sees at first use. Re-configuring without reset_config! is silently ignored.
  • Result#phone is always the NORMALISED phone except in the :invalid_phone_number rescue, where normalisation failed and the raw input is returned.

Non-obvious coupling

  • TestAdapter and TwilioAdapter both import Result and Token directly. Adding a third adapter (Vonage, MessageBird) means the same two imports.
  • The Controller concern reads session[:bitsmithy_auth_token]. Any host app that touches this key directly couples to the concern's session contract.
  • RailsEnvStub lives in test/support/. It's installed at the TOP of test_helper.rb so it's defined BEFORE bitsmithy/auth loads. If you ever do real require "rails" in tests, RailsEnvStub will conflict.
  • Phone.parse is private-by-convention (no private_class_method). If you make it public to extend Phone, audit every other module.

Gotchas

  • Phonelib rejects 555-area-code US numbers as "not real" (correctly — they're reserved fictional). Don't use +15555551234 in tests; use +12127363100 or another real-looking number.
  • The mocha stub on Time.now must compute the future timestamp BEFORE the stub is installed. Time.stubs(:now).returns(Time.now + N) evaluates the inner Time.now AFTER stubbing, returning nil.
  • JWT 3.x reads error code from response.body["code"], not response.error_code. The test helper for Twilio errors knows this — don't break it.
  • TwilioAdapter.map_status_code currently covers 500..529 only — 530..599 falls through to :twilio_error. Fix this before tagging v0.1.0.

Don't forget

  • v0.2.0 work that's already documented as out-of-scope: Mountable Rails engine, install generator, default ERB views, Redis-backed Store, voice/WhatsApp channels.
  • When you ship auth-python and auth-go, ADR-0006 binds them to the same naming shape. The Token's iss: "bitsmithy-auth" claim is the cross-language anchor — don't change it.
  • The fact-check pass discovered a 5xx coverage gap (530+). Open an issue against v0.1.0 to widen the range to 500..599 OR document the gap deliberately.
  • The PRD and tasks documents were fact-checked and corrected after implementation. They are now the canonical reference; if you change behaviour later, update them too.
