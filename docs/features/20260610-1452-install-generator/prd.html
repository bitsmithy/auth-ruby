Product Requirements Document

Install Generator

A single rails generate bitsmithy:auth:install command that scaffolds everything a Host app needs to render the Engine's sign-in flow.

Problem & Solution

After mounting the Engine, a Host app must create three things from scratch: an initializer with the four required config fields, two view templates with the correct locals and route helpers, and the mount line in routes. Each step is documented but not automated.

The generator turns this from a read-copy-paste exercise into a single command. Developers own every generated file and are free to edit them — the generator is a starter, not a jail.

Generated Files

  • ▶ config/initializers/bitsmithy_auth.rb Create
  • ▶ app/views/bitsmithy/auth/sessions/new.html.erb Create
  • ▶ app/views/bitsmithy/auth/sessions/edit.html.erb Create
  • ▶ config/routes.rb Insert mount line
Initializer
Production config with Twilio credentials from ENV vars; dev/test auto-enables test_mode! with a dummy signing key. Commented-out optional overrides for after_sign_in_path, on_verified, etc.
Phone Form
Text input with inputmode="tel", posts to send_code_path, displays @error when re-rendered.
Code Form
Text input for the six-digit code, posts to verify_path, displays @error and @phone.
Route Insertion
mount Bitsmithy::Auth::Engine => "/auth" added after the Rails.application.routes.draw opening. Skipped if already present.

User Stories

  1. Run one command. As a Host app developer, I want to run one generator command, so that I get a working initializer, view templates, and the mount line without reading the README.
  2. Production config from ENV. As a Host app developer, I want the generated initializer to configure Twilio credentials from ENV vars in production, so that my production setup is secure and follows Rails conventions.
  3. Auto test mode. As a Host app developer, I want the generated initializer to enable test mode in development and test environments automatically, so that I can develop and test without Twilio credentials.
  4. Renders immediately. As a Host app developer, I want the generated Phone-form and code-form templates to render with the correct form action and locals out of the box, so that the sign-in flow works immediately after generation.
  5. No duplicate mount. As a Host app developer, I want the mount line inserted into config/routes.rb without duplication if already present, so that routing works without manual editing.
  6. Idempotent. As a Host app developer, I want the generator to be idempotent — re-running it does not duplicate the mount line or overwrite my edited templates — so that it is safe to run again after upgrading the gem.
  7. Force reset. As a Host app developer, I want a --force flag to overwrite existing files when I intend to reset them, so that I can regenerate the defaults on demand.
  8. Safe upgrades. As a Host app developer upgrading the gem, I want to re-run the generator to get an updated initializer without losing my view templates, so that upgrades are low-risk.

Implementation Decisions

Module
InstallGenerator
A Rails::Generators::Base subclass at Bitsmithy::Auth::Generators::InstallGenerator. Namespaced under the gem's module, registered only when Rails::Generators is defined — mirrors the existing Rails::Engine and ActionController conditional guards. Non-Rails consumers never load it.
Contract
Template ERBs
Three source templates shipped under lib/generators/bitsmithy/auth/templates/: initializer.rb.erb, new.html.erb, edit.html.erb. The initializer branches on Rails.env.production? for ENV-based Twilio config vs. test_mode!.
Behaviour
Idempotence & Overwrite
Standard Rails generator defaults: existing files are skipped unless --force is passed. The mount line insertion reads config/routes.rb and checks for existing mount Bitsmithy::Auth::Engine — never duplicated.
Boundary
No User Model, No Migration
Consistent with ADR-0003 and ADR-0007. The gem is a verification primitive; the generator scaffolds only what the Engine needs to render. No User model, no database migration, no sessions table.

Scope

In scope
  • Initializer scaffolding
  • View template creation
  • Route insertion
  • --force flag support
  • Conditional load guard
Out of scope
  • User model or migration
  • Eject / customise controller
  • Non-Rails rake task
  • Shipping views in gem load
  • New runtime dependencies

Testing Decisions

Use Rails::Generators::TestCase with a minimal Rails application scaffold — no database, no real routes. Tests assert created file existence, file content markers, and idempotence:

  • Initializer exists with production/ENV and dev/test guard markers
  • Both view templates exist at expected paths
  • Mount line present in routes.rb
  • Running twice does not duplicate mount line or overwrite files
  • --force overwrites existing files

No prior generator tests exist in this codebase; these follow standard Rails generator testing conventions.

ADR Note

ADR-0008 says the engine ships no views. The generator scaffolding views into the host app does not violate this — it creates host-owned files that the user is free to edit, eject, or delete. The engine itself still has zero views. A new ADR codifies this distinction.
